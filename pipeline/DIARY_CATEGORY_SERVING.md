# 오늘의 식단: 카테고리 표준 1인분 (2026-11-12)

이번 기능은 `web/meal-serving-rules.json`의 사용자 지정 표만 제공량으로 사용한다.
DB의 `servingWeight`, `1회 섭취참고량`, 포장 내용량을 읽지 않는다.
기존 학식 계산용 `build_month.py`는 수정하지 않았다. 그 파일의 볶음밥 210g·국/찌개 통합 272mL와 달리 새 일지 버튼은 이번 요청의 볶음밥 289g·국/탕 288mL·찌개/전골 201mL를 사용한다.

## 적용

- 선택한 영양 DB 레코드의 `basis`로 g 또는 mL를 결정하고 같은 단위의 표준량만 사용.
- 한 단위만 제시된 미니 면류 120g·파스타 172g·소스 9mL는 반대 단위에 적용하지 않음(사용자 확인).
- 제육볶음 등 메인 단백질은 반찬 볶음 80g 대신 151g 사용(사용자 확인). 생선구이는 70g.
- 잡채는 mL 레코드에서 150mL, g 레코드에서는 일반 반찬 72.2g.
- 미니/꼬마의 DB 자체 제공량 상속 없음. 미니 명칭이 검색되지 않으면 해당 접두어만 제외해 같은 이름의 영양자료를 찾고, 명시된 미니 분량은 유지한다. 다른 재료명의 임의 치환은 하지 않음.
- `부대찌개&라면사리` 같은 검색은 추가면 부분을 제외하고 본 메뉴만 찾음. 사리 단독은 자동 1인분에서 제외하며, 실제 섭취한 양의 직접 기록은 가능.
- 원재료, 분말·원액·농축제품, 조리 전 생면·건면·숙면 등은 조리완성식 표준량으로 계산하지 않음. 제공량을 식별할 수 없는 음식도 직접 입력으로 안내.
- 과거 기록의 섭취량·영양값은 자동 변경하지 않음. 신규 적용 값과 출처는 기록의 `servingReference`에 함께 저장.

## 검색 우선순위

동일한 이름 일치 수준 안에서 반찬은 외식 g 분석 → 가정식 g 분석 → 기존 레시피 계산값 → 가공 → 원재료 순.
국물·밥·면·장류양념은 산업체급식 우선. 다른 g/mL 레코드도 남겨 사용자가 출처를 보고 선택할 수 있다. 선택된 레코드를 다른 DB로 자동 교체하지 않는다.
정확한 이름을 단순 포함 후보보다 우선하며, 재료가 다른 변형 메뉴를 동일 음식으로 확정하지 않는다.

기존 검색 카탈로그와 영양소 원본은 변경하지 않았다. 레시피 검색은 `pipeline/master_cache.json`에 이미 산출된 `recipe_decompose` 27건만 별도로 내보낸다. 레시피 자체 제공량은 사용하지 않는다. 영양정보가 부분 추정인 12건은 미확인 표시를 보존한다. 전체 레시피 DB 1,156건이 모두 연결됐다는 의미가 아니다.
캐시 갱신 후 `python pipeline/build_meal_recipe_index.py`로 `web/meal-recipe-index.json`을 다시 생성한다. 레시피의 새로운 영양값을 추정하거나 원본 캐시를 덮어쓰지 않는다.

## 변경 파일

- `web/index.html`: 규칙표·스크립트 연결
- `web/meal-diary.js`: 버튼, 단위별 적용, 출처·기록 메타데이터
- `web/meal-food-search.js`: 후보 출처 정렬 및 기존 레시피 연결
- `web/meal-serving.js`: 카테고리 판정·동일 단위 조회·검색 정책
- `web/meal-serving-rules.json`: 사용자 지정 중량표
- `web/meal-recipe-index.json`: 기존 레시피 per100 검색 스냅샷
- `pipeline/build_meal_recipe_index.py`: 스냅샷 생성기
- `web/meal-serving.test.cjs`, `web/meal-serving.e2e.cjs`: 회귀 검증
- 이 문서

정적 서버에서 `web/`를 실행한다. Node 검증은 `node --test web/meal-serving.test.cjs`, Playwright 브라우저 검증은 `node web/meal-serving.e2e.cjs`. `HYU_TEST_URL`, `HYU_SERVING_OUTPUT`으로 테스트 URL과 보고서 위치를 변경할 수 있다. 테스트는 격리된 가상 사용자와 가상 기록만 사용한다.
